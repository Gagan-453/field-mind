# FieldMind — project instructions

Tick-based agentic monitoring system for a 67 TPH AFBC bi-drum boiler. Runs
offline on a Qualcomm QIDK (SM8650) via LiteRT. Embedded Systems Workshop,
Lab 2, Project 4. Advisor Prof. Priyesh Shukla, TA Aryama Murthy.

The research question is how to schedule heterogeneous agentic LLM workloads
across NPU, CPU and DSP under offline, latency and power constraints. The agent
is the vehicle; the scheduling study is the contribution.

---

## Non-negotiables

**No invented numbers.** Every constant in the simulator must be one of three
things, and a comment must say which:

1. **Derived** — from geometry or thermodynamics, with the derivation shown
2. **Cited** — to `docs/FieldMind_Boiler_Agent_Plan.pdf` or a case study PDF,
   with the section
3. **Fitted** — to `data/reference/fingerprint.json`, with the fitting method

A number that is none of these does not go in. If you need a value and cannot
source it, stop and say so rather than picking something plausible.

**No fabricated results.** Never report a metric that was not produced by an
actual run. Energy figures require the device; leave them `null` on mock and
cloud backends rather than estimating. An invented energy number silently
becomes the headline result, because the headline metric is energy per correct
diagnosis (S3/Q2).

**Mock-backend numbers are not agent results.** The mock backend re-ranks
retrieved cases and does no reasoning. Its output measures the deterministic
and retrieval layers only — that is the baseline the LLM has to beat. Say so
every time those numbers are quoted.

**All plant data is synthetic.** Generated by `data/generator/`. The agent is
advisory only and never actuates anything.

---

## The two structural invariants

Almost every design decision follows from these. Do not break them.

1. **The model never sees raw numbers.** L1 turns sensor readings into Facts;
   the prompt contains Facts. This is both a quality decision (models are bad
   at arithmetic over long number sequences, good at weighing explanations) and
   a cost one (4,300 numbers per tick becomes 150–300 tokens, which is the
   difference between fitting the NPU's compiled static shape and not).

2. **The model never has the last word.** L6 validates every cited fact ID
   against what L1 actually emitted, and actions come only from a fixed
   catalogue. Plant state — which drives escalation — is derived from facts,
   never from the model.

## The three frozen contracts

- **Episode** — the harness reads episode files in timestamp order and never
  exposes anything from the future.
- **Fact** — L1 is the sole producer. Everything downstream, including the LLM,
  may only cite Fact IDs that L1 emitted.
- **Action** — L6 is the sole producer, drawn only from
  `data/kb/action_catalogue.json`. The model selects; it never writes a
  procedure.

```
data/kb/         asset_model, case_library, action_catalogue
data/episodes/   generated — 30 episodes, gitignored
bench/           harness, evaluator, validate_data, probe_device, tests
device/          QIDK push scripts and model files
results/         generated, gitignored
```

The agent core (`fieldmind/`) is **stdlib-only on purpose** so it can be copied
to the device without a scientific Python stack. PyYAML is the only runtime
dependency and it only reads the config. Do not add imports there.
`data/generator/` and `bench/` run on the host and may use numpy/pandas.

## Reference data

`data/reference/xinan_completed_data.csv` — 86,400 rows, 5-second sampling,
120 hours of continuous operation from a real AFBC-class boiler at ~60 t/h,
9.77 MPa, 537 °C main steam, 774 °C bed. Same sample period we use.

This is the calibration target. Column mapping (verified):

| our tag | their column | notes |
|---|---|---|
| `steam_flow` | `ZZQBCHLL.AV_0#` | main steam flow, t/h |
| `bed_temp_avg` | `TE_8313B.AV_0#` | bed temperature, °C |
| `ms_temperature` | `TE_8332A.AV_0#` | main steam temperature, °C |
| `drum_pressure` | `PTCA_8322A.AV_0#` | MPa — convert, we use kg/cm²(g) |
| `drum_level` | *(absent)* | no equivalent; must be derived |
| `feed_water_flow` | *(absent)* | no direct equivalent |

**Known calibration gap, measured 2026-08-31.** Our synthetic noise is wrong in
both directions at once:

| | ours per-sample | real per-sample | ours lag-1 ac | real lag-1 ac |
|---|---|---|---|---|
| bed temperature | 1.716 °C | 0.273 °C | 0.775 | 0.9997 |
| main steam temp | 1.129 °C | 0.067 °C | 0.210 | 0.9999 |
| main steam flow | 0.478 t/h | 0.188 t/h | 0.767 | 0.9969 |

Real tags barely move sample-to-sample but wander widely over hours — bed
temperature has a 5-day standard deviation of 10.68 °C with near-perfect
autocorrelation. Ours jitters around a tight mean (episode sd 2.56 °C). Every
RATE check, MAD and slope estimate is currently calibrated against the wrong
noise model, and family E's ~40 °C drift is a 15-sigma signal against our
variability where it would be about 4 sigma against real variability.

Correction to fingerprint gap 3: the 255 min / 707 min figures are the
autocorrelation of the level, which is inherited from slow load variation
(steam flow's own tau is 27 min). Increment cross-correlation shows the
steam->bed response peaks at lag 0, so the plant responds in minutes.
Do NOT slow bed or ms relaxation by 30-170x; that would break families
C and D. Reproduce the long autocorrelation with slow stochastic drift in
the DRIVERS instead (gap 4).

## Case study PDFs

`docs/Boiler_Failure_Case_Studies_RCA.pdf` — **18 cases, AFBC captive boiler.
This is the right asset.** Six families: water-side control, steam-side

Source the case library from this. Decide the hold-out split with the advisor

`docs/Boiler_Tube_Failure_RCA_DSPM_Korba_East.pdf` — 6 cases, 2×250 MW

## Known bugs — fix before trusting any LLM benchmark

1. **DEGRADED latch.** `orchestrator.py` sets `wm.degraded_mode` on any non-ok
   LLM reply and nothing ever clears it. `derive_state` then returns DEGRADED
   for the rest of the episode, swallowing every NORMAL and DEVIATION tick.
   Ground truth never contains DEGRADED, so all of them score as errors. One
   failed API call turned `ep_N01_normal` into 56 false positives out of 80
   ticks. `trusted_tags` has the same latch — a VALIDITY fact removes a tag and
   nothing restores it.

2. **`_merge` discards the belief accumulator.** It does `out = dict(model)`,
   so the model's hypothesis list replaces the deterministic one wholesale and
   the cross-tick log-odds accumulation is thrown away whenever the LLM
   answers. Symptom: 9.5 distinct actions proposed per episode from a 16-action
   catalogue with `max_actions: 3` per tick.

3. **`records.json` never reaches the agent.** `build_agent(cfg, notes)` only
   takes notes. Eight of 30 episodes list records as a required modality.

4. **`query.txt` is never read** by anything.

5. **Tier counts drifted** — 13/10/7 on disk against 12/12/6 intended.

6. **`update_hypotheses` matches on tag name only**, discarding direction and
   band, while `CaseLibrary.match` compares full triples. At `ep_A01` tick 76
   this charges the correct hypothesis −0.90 for its own confirming evidence.

## The backend switch

One line in `configs/base.yaml`: `llm.backend: mock | gemini | litert`.
Everything downstream calls `backend.generate(prompt, role=...)` and gets a
uniform `LLMReply`. `fieldmind/runtime/llm_backend.py` is the only file that
knows how a model is invoked. Adding Genie or llama.cpp means one class with
one method plus `register_backend()`.

Current model is Gemma3-1B-IT q4. **Assume it will be swapped.** Never
hard-code a model name outside the config. The `latency_ms` / `backend` /
`model` / `tokens` fields on `LLMReply` are not decoration — they feed the
per-stage cost model for the scheduling study. Fill them in on every backend.

Device gotchas that fail *silently*: `LD_LIBRARY_PATH` and
`ADSP_LIBRARY_PATH` must be in every `adb shell` invocation or the binary
quietly falls back to CPU; prompts must be pushed as files, not passed as shell
arguments, because they cross two shell layers. Run `bench/probe_device.py`
before trusting any device number.

## Working style

- Move one stage at a time. Show the numbers before moving on.
- When something looks wrong, check it against the physics or the reference
  data rather than adjusting until output looks plausible. Five real simulator
  bugs were found that way and each had silently broken a whole fault family.
- Surface gaps proactively. The README lists known gaps with an instruction not
  to report around them — keep that habit.
- Prefer editing existing files over creating new ones. Do not add documentation
  files unless asked.
---

## Verification protocol — applies to every file, every time

Before showing me any file or claiming any result:

1. **Run it.** Execute the module or a driver that exercises it. Paste the full
   output, not a summary.
2. **Run its self-tests.** Paste the full output.
3. **Re-derive one headline number by a method the code does not use.** Not a
   rearrangement of the same expression — a different route to the same
   quantity. Report both values and the relative difference.
4. **Mutation-check the tests.** Corrupt one constant the tests should catch,
   confirm a test actually fails, restore it, and report which test caught it.

If any step fails, fix it and repeat before asking. Do not present a file that
has not been run.

**A test that still passes when you break what it tests is not a test.** Two
have already shipped in this project: a "K by an independent route" check that
was the same algebra rearranged, and a shrink-and-swell direction check that
recomputed swell from the same pressure means it was testing. Delete or replace
any test that cannot fail.

**Test outcomes, not expressions.** Assert against the emitted trace or the
returned state, never against the formula that produced it.

## Sign discipline

State the expected **direction** of every physical response *before* writing the
code, then verify it against the emitted trace.

Three of the four bugs in the original simulator were sign errors, and each one
silently broke an entire fault family:

- a tube leak modelled as *heating* the bed instead of cooling it
- a water-balance residual whose text said "feed is short" when it meant
  "water is being lost"
- a drift check that was not load-normalised

Known-correct directions, for reference:

- load increase → pressure falls → voids expand → level **rises** (swell);
  load decrease → **shrink**
- tube leak → water into the furnace → bed **cools**
- leak or stuck-open blowdown → conductivity **falls**;
  feed shortage at normal blowdown → conductivity **rises**
- fuel availability capped → pressure sags → turbine throttles → steam **falls**

## The tuning prohibition

**Never choose an input to reproduce a target number.**

If a derived value disagrees with a prior value, a case study, or an
expectation, **record the disagreement**. Do not adjust assumed inputs to close
it. This project has already caught one instance: reconciling drum dimensions
to reproduce `K_LEVEL = 0.22` would have laundered an invented constant into a
"derived" one, and the real finding — that no plausible drum geometry produces
0.22 — would have been lost.

Every ASSUMED constant must carry a range and a statement of what it affects.
A value with no range is not ASSUMED, it is invented.

---

## Stop rules — halt and ask rather than proceed

Stop and write the question into the report when any of these occur. Do not
pick a plausible value and continue.

1. A constant cannot be derived, cited, fitted, or bounded to a defensible
   ASSUMED range.
2. A derived value disagrees with a case study, a prior value, or a physical
   expectation by more than 2×.
3. A direction check fails, or a self-test fails and the fix is not obviously
   a transcription error.
4. A design decision would change what the benchmark measures — tag set,
   episode structure, metric definitions, ground-truth format.
5. A change would touch `configs/base.yaml` thresholds, episode severities, or
   anything else tuned against the old physics, outside a stage explicitly
   scoped to re-tune it.
6. Two requirements conflict and satisfying both is impossible.

When stopped, keep going on anything independent of the blocked item, and list
the blockage in the report.

---

## Report — write after every sub-model or stage

Write to `reports/<stage>_<submodel>.md` and commit it. Format:

```markdown
# <stage / sub-model> — report

## Status
DONE | BLOCKED | PARTIAL — one line on what was built.

## Verification
| step | result |
|---|---|
| ran the module | pass/fail + key output |
| self-tests | n passed / n failed |
| independent re-derivation | quantity, both values, relative difference, method used |
| mutation check | constant corrupted, which test caught it |

## Direction checks
One row per sign claim: expected direction, measured value, OK/FAIL.
Mark any check that depends on not-yet-rewritten code as PROVISIONAL.

## Constants introduced
| symbol | value | provenance | range | affects |
Every ASSUMED entry needs a range and an "affects" column.

## Numbers that changed
Old value, new value, ratio, and what downstream depends on it.

## Disagreements recorded, not resolved
Anything that conflicts with a case study, a prior value, or an expectation.
State both sides and which was chosen, and why. Do NOT resolve by tuning.

## Blocked / needs a decision
Stop-rule hits. State the question and the options, not a recommendation
already acted on.

## What I could not verify
Anything taken on trust, and what would be needed to check it.
```

The last two sections are the point of the report. A report with both empty is
a signal to look harder, not a clean bill of health.
